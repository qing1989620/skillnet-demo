## 一、修改的文件与原因

### 核心算法

| 文件 | 修改 | 原因 |
|---|---|---|
| `skillnet/bandit.py` | **完全重写** | 原实现是 per-arm LinUCB（每技能独立的 A/b），在数学上**不可能**让「评估 A 的反馈影响未评估的 B」，但文档却这么声称。同时 `predicted_reward` 恒为 0（b 初值为零向量），意味着它从未真正学习过。改为 **shared LinUCB**：全局共享 A/b/θ，φ 编码 (task, skill) 对 |
| `skillnet/bandit.py` | 上下文编码器重做 | 原 `ContextEncoder` 只编码技能、**不编码 task**，且用内置 `hash()`（受 `PYTHONHASHSEED` 影响，每进程结果不同）。新 φ = task 词袋(64) + skill 词袋(64) + domain one-hot(24) + 交互(3) + 元特征(5) = 152 维，全部走 CRC32 |
| `skillnet/retriever.py` | 加降级可观测 | 缺密钥时 fabric 会**静默**跳过 LLM 重排，使用者看到 `mode=fabric` 就以为重排生效了。现返回 `degraded` / `components` / `degraded_reason` |
| `skillnet/retriever.py` | 权重注释 | 代码是 0.70/0.20/0.10，文档写 0.55/0.30/0.15 —— 数字漂移 |

## 二、修复的问题

### P0（阻断级）

1. **bandit 不学习** —— `predicted_reward` 恒为 0。修复后实测：
   `0 → 0.524 → 0.618 → 0.689 → 0.707 → 0.731`（单调增长），
   探索奖励同步从 0.2518 衰减到 0.1592。
2. **bandit 无跨技能泛化** —— per-arm 结构决定的不可能。修复后：只更新 A，
   同领域技能 B 的预测变化量是异领域 C 的 **1.24 倍**（Δ0.701 vs Δ0.565）。
3. **上下文不可复现** —— 内置 `hash()`。修复后两个不同 `PYTHONHASHSEED` 的子进程输出一致。
4. **benchmark leakage** —— dev/heldout 未分离。分离后**dev 的高分被证明含过拟合**
   （见下方实验结果）。
5. **数字漂移** —— 建立单一数据源，`--check` 可自动发现不一致。

### P1

6. 实验三把不可区分的结果包装成 RL 收益 —— 现输出配对 bootstrap CI，
   跨 0 时明确写「不可区分，本实验仅验证闭环」。
7. 降级静默 —— 现 API 返回 `degraded` / `components`。
8. ZIP 中文文件名跨平台问题 —— 顶层文件全部 ASCII 化（内容仍中文）。

## 四、实验结果

### 4.1 检索与编排（dev vs held-out）

| 指标 | dev（调参集） | held-out（冻结集） |
|---|---|---|
| BM25 召回 | 77.5% | 73.6% |
| hybrid 召回 | 78.3% | 76.4% |
| fabric 召回 | 95.8% | **86.1%** |
| fabric 完全覆盖 | 90.0% | **66.7%** |
| fabric 编排完整度 | 92.5% | **25.0%** |

**这是本轮最重要的发现。** 编排完整度从 92.5% 掉到 25.0%，
说明 dev 集的高分里有相当一部分来自过拟合（融合权重与关系扩展参数是在 dev 上调的）。
held-out 任务的依赖链更长，而技能库只有 62 条人工定标的关系边，覆盖不到就推不出顺序 ——
**技能关系图的覆盖度是当前最薄弱的环节**。

### 4.2 执行质量（dev，12 任务 × 4 档 × 3 次重复）

| 技能供给 | 盲评均分 | skill-derived reference coverage | 采纳率 |
|---|---|---|---|
| 无技能 | 8.22 | 81.3% | — |
| 仅技能卡 | 8.52 | 88.0% | 89.4% |
| 混合检索 | 8.79 | 90.6% | 65.6% |
| 完整方案 | 8.86 | 92.8% | 88.9% |

四档单调递增。注意指标已正名：参考要点抽自技能库自身的 pitfalls/verification，
而技能组又会读这些技能，**存在同源偏置**，不能称为「客观指标」。

### 4.3 选择与进化（重跑，新 bandit）

| 策略 | 平均奖励 | 标准差 |
|---|---|---|
| Shared LinUCB | 0.8275 | ± 0.0557 |
| 随机选择 | 0.8642 | ± 0.0447 |

配对 bootstrap（4000 次重采样）：均值差 **-0.0367**，95% CI **[-0.0892, 0.0217]**，**跨 0**。

**结论：两组不可区分。** 本实验只验证「选择 → 执行 → 奖励 → 更新 → 进化」闭环可运行，
**不构成「选择策略优于随机」的证据**。证据等级：Preliminary。

## 五、尚未解决的问题

### 未做（有意识取舍）

1. **held-out 的 exp2 / exp3 未跑** —— 需要 API 预算与时间。当前 held-out 只有 exp1。
   下游后果：报告里「技能提升执行质量」的结论仍基于 dev 集，属于**偏乐观**的证据。
2. **Skill 生命周期治理未实现** —— 用户要求的 candidate → evaluated → approved →
   active → deprecated 状态机、approve/reject UI、Candidate Queue 都没做。
   当前 `evolve()` 仍是直接入库。
3. **Demo 信息架构未重做** —— 首页仍是报告目录式，Hero Demo 的五阶段叙事没有实现。
4. **独立评价来源未接入** —— 用户要求优先做 sandbox/产物级判分。
   当前仍只有 LLM judge + skill-derived reference coverage。
   这是 v0.4 最该做的第一件事。
5. **模型层未抽象** —— 仍绑定 DeepSeek；`ModelProfile` / `PricingProfile`
   虽在 yaml 里声明了计价版本，但代码未按 profile 计算，UI 也没标 "estimated cost"。
6. **pytest 覆盖不足** —— 只有 bandit 一组测试（6 个）。
   API smoke / 持久化 / 并发 / 安全 / 降级模式都还没写进 pytest。
7. **CI 未配** —— 无 `.github/workflows`。

### 已知但不打算改的

- **稀疏向量代替稠密编码器**：运行环境无法下载模型。语义通路是降级实现，
  融合权重 0.70/0.20/0.10 是**针对这个降级实现**标定的，接入稠密编码器后必须重新标定。
- **exp3 轮次少（6 轮）**：COBRA-Skills 用 30 轮 × 50 样本。
  在方案级评估下，即使加到 30 轮，奖励分辨率仍然不够 —— 这不是样本量问题，
  是**评估层级**问题。所以优先级应放在「换到产物级评估」而不是「多加轮次」。
