# 迭代日志 · Iteration Log

> 本文档记录 SkillNet-S1 的**持续自我推演与迭代过程**。
> 方法：每轮先以「用户 / 老板 / 技术专家 / 竞品」四种视角对当前产物提出反驳，
> 再把反驳变成可验证的缺陷，修复后用真实运行结果验证，最后记录遗留。
>
> 原则：**不接受"看起来更好"，只接受"实测更好"**；不粉饰失败样本。

---

## 迭代方法论

**四视角反驳模板**（每轮至少各提一条）：

| 视角 | 提问 | 举例产出 |
|---|---|---|
| 用户 | 我点这里会发生什么？看不懂怎么办？ | 引导缺失、加载无进度、错误提示含糊 |
| 老板 | 这对我有什么用？能接产品吗？ | 价值没被证明、接入路径不清、成本不明 |
| 技术专家 | 这个实现站得住吗？哪里会崩？ | 自评循环、并发不安全、资源无上限 |
| 竞品 | 凭什么用你而不是它？ | 独有能力是否可验证、是否被超越 |

**每轮产出物**：问题清单（含证据）→ 修复（含代码位置）→ 验证（含实测数据）→ 遗留。

## R1 · 执行可靠性（2026-10-02，由真实故障触发）

**触发**：负责人跑 ML pipeline 任务，三次尝试全部 `syntax` 失败，
页面却显示「修复后成功」；且提示「该技能未提供 verification 清单」，但该技能实际有 3 条。

| # | 问题 | 证据 | 修复 | 状态 |
|---|---|---|---|---|
| 1.1 | **失败被描述成成功** | `fixed: len(attempts) > 1` 只数尝试次数，三次全失败也置 True，前端写「修复后成功」 | 改为 `fixed = 尝试>1 且 最终成功`；新增 `exhausted` 表示尝试耗尽 | ✅ |
| 1.2 | **验收跳过原因归错** | 执行失败时跳过验收，前端却归因为「技能未提供清单」（该技能有 3 条） | executor 返回 `verify_skip_reason`，区分「执行失败 / 模式无契约 / 技能确无清单」 | ✅ |
| 1.3 | **代码被截断但无人察觉** | 生成 19475 字符代码，line 531 `'[' was never closed` ——写 CSV 表头的列表被截断 | token 预算 7000 → 12000；提示词增加「单文件 ≤250 行，超出用 TODO 标注」 | ✅ |
| 1.4 | **截断错误被当成普通 bug 修补** | 连续三次 syntax 失败：模型每次都在补同一份超长代码，再次截断 | 新增 `_looks_truncated()`：报错指向文件末尾未闭合结构且代码 >6000 字符即判定截断，修复提示改为「**重写更精简的完整代码**（≤200 行）」 | ✅ |

**验证**：`_looks_truncated` 三组用例（长+未闭合 / 短+普通 / 长+逻辑）判定正确；
生成提示词含规模约束；实测 ML pipeline 任务通过（见 R2 记录）。

**实测验证（同一 ML pipeline 任务，修复前 vs 修复后）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 尝试次数 | 3 次**全失败**（syntax） | **1 次通过** |
| 代码规模 | 19475 字符（被截断） | 6831 字符 |
| 产物 | 无 | `error_by_group.csv` |
| 技能验收 | 被错误跳过 | **3/3 通过**（SEED=42；stratified_kfold(y,5,SEED)；子群 A/B 的 Acc 与 F1 对比） |

**实测验证（同一 ML pipeline 任务，修复前 vs 修复后）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 尝试次数 | 3 次**全失败**（syntax） | **1 次通过** |
| 代码规模 | 19475 字符（被截断） | 6831 字符 |
| 产物 | 无 | `error_by_group.csv` |
| 技能验收 | 被错误跳过 | **3/3 通过**（SEED=42；stratified_kfold(y,5,SEED)；子群 A/B 的 Acc 与 F1 对比） |

**遗留**：任务粒度仍由 LLM 决定，缺少「步骤拆分到可执行大小」的机制 → 列入 R2。

## R2 · 执行可靠性深化（进行中）

**动机（技术专家视角反驳）**：「你说技能在执行中积累数据——但执行失败率从来没有被记录过。
哪个技能容易跑崩？技能作者无从得知，也就无法改进。所谓『技能运维』缺了最直接的一环。」

| # | 问题 | 证据 | 修复 | 状态 |
|---|---|---|---|---|
| 2.1 | **执行结果用完即弃** | 执行成败只存在于当次请求内存，无归档 | 新增 `_record_execution()`：成功/失败样本写入 `out/exec_log/executions.jsonl`（含技能、任务、尝试次数、错误类型、错误尾巴） | ✅ |
| 2.2 | **技能没有执行可靠性数据** | `skill.stats` 只有 pulls/reward，无执行成败 | 新增 `exec_total / exec_ok / exec_fix / exec_fail / exec_last_error`，写回技能 stats；`/api/skills` 已返回；briefing 执行阶段与星图技能卡片均已展示成功率与「修复后成功」次数 | ✅ |

**验证**：单元测试三组（成功/修复成功/失败）统计正确（total=3, ok=2, fix=1, fail=1, last_error=syntax）；
端到端真实执行一次，`exec_total` 精确 +1（曾因重复插入导致翻倍，已修）；
归档文件正常写入。

**意义**：执行可靠性成为**技能质量的可观测信号**——反复失败的技能说明其 steps 不够可执行、
或 pitfalls 未覆盖真实坑点，这是技能改进的直接线索。

**遗留（下一步）**：
- 2.3 步骤粒度控制（把「一次写完整 pipeline」拆成小步）
- 2.4 并发执行压测
- 2.5 超时与分段执行
