## 零、背景与结论摘要

开发组另一成员提供了一套完整的技能执行系统（下称 **Nexus**，解压于 `../_member_ref/`）：
FastAPI 后端 + Streamlit 前端 + 24 个技能 + Chroma 向量库 + 29 个测试文件（5000+ 行测试）。

**它比本项目大得多，也更生产化。** 本轮的判断是：**互补而非替换**——
两套系统的定位不同，Nexus 解决「用技能干活」（检索 → 规划 → 执行 → 产出文档），
本项目解决「技能怎么管、怎么度量、怎么变好」（资产化 → 策略 → 评估 → 进化）。
因此本轮做三件事：**把它的技能资产并入我们的库、把它验证过的产品决策逻辑吸收进来、
把它的工程经验对照出我们的差距**。

结论：

| 技能库 | 51 → **75 技能**，17 → **22 领域**，62 → **90 条关系边** |
| 新增产品能力 | **检索置信度分流**（自动执行 / 人工确认 / 无匹配直答） |

## 一、跨项目技能扩容（51 → 75）

### 做了什么
把 Nexus 的 24 个技能转换为本项目的 Skill Contract 格式并入库：

- **Anthropic 官方技能套件（19 个）**：docx / pdf / pptx / xlsx / doc-coauthoring /
  skill-creator / mcp-builder / claude-api / webapp-testing / web-artifacts-builder /
  canvas-design / brand-guidelines / algorithmic-art / frontend-design / theme-factory /
  slack-gif-creator / internal-comms / academy-guide / discernment-nudge
- **中文自制技能（5 个）**：code-helper / contract-review / interview /
  leetcode-hot100-coach / algotrace

新增 5 个领域：**文档工程（6）、技能工程（6）、设计与创意（6）、职业与学习（4）、知识与合规（2）**。

### 关键设计：建立跨领域关系边
单个技能入库只是加法，**把工具技能与科研方法技能连起来才是价值**：

| 关系边 | 语义 |
|---|---|
| `docx` ↔ `scientific-writing` | 科研写作的产出需要 Word 交付 |
| `pdf` ↔ `literature-review` | 文献综述的输入输出都走 PDF |
| `pptx` ↔ `poster-slides` | 学术汇报的幻灯片交付 |
| `xlsx` ↔ `eda-profiling` | 表格数据分析的载体 |
| `canvas-design` ↔ `scientific-visualization` | 学术海报与图表设计 |
| `contract-review` ↔ `docx` | 合同审查产出 Word 修订稿 |

结果：技能库从「只会科研方法」变为「**科研方法 + 交付物产出**」的完整体系——
这正是 Nexus 的规划器要解决的问题（一个任务往往既需要方法技能也需要交付技能）。

### 实现
- 转换脚本：`tools/import_member_skills.py`（幂等，可重复运行）
  - 从原文 frontmatter 与正文提炼契约字段（capability / use_when / steps / pitfalls / verification）
  - 五维质量按可提取的信息量评级，并加 `member_import=true` 标记
  - 生成 SKILL.md（供导出与跨框架互操作）+ 注入 `seed/catalog_data.py` 的 `S(...)` 条目
  - 关系边做对称去重，避免图上出现重复边
- 诚实性约定：领域划分与关系边由本项目补充；契约字段依据原文提炼，
  **无法从原文确定的字段给出保守值并在技能正文注明**；不编造原文没有的信息。

### 验证
- 技能库加载 75 个 / 22 领域 / 90 边，verify.py 31/31 通过
- 新技能检索命中 **6/6**：
  「导出 Word」→ docx（带出 doc-coauthoring、scientific-writing）
  「演示文稿」→ pptx（带出 poster-slides、theme-factory）
  「Excel 表格」→ xlsx、「学术海报」→ canvas-design、
  「算法面试」→ interview、「合同风险」→ contract-review

## 二、检索置信度分流（吸收 Nexus 的混合调度设计）

### 它做了什么
Nexus 用 Top-1 余弦相似度分三档决定下游动作：
`≥0.5` 自动执行 / `0.3–0.5` 人工确认 / `<0.3` 无匹配直答。
这是**产品化决策逻辑**，比「检索完就直接执行」严谨——本项目此前缺失这一层。

### 吸收过程中的关键发现（本轮最有价值的技术结论）
直接照搬阈值是不行的，因为**分数体系不同**。更关键的是：本项目原有的
「融合分」经过 min-max 归一化，**对候选池组成敏感、跨查询不可比**——
同一个技能在不同查询下分数尺度不同。用它做绝对阈值会得到荒谬结果
（实测：「我要写一份合同」融合分只有 0.128，而库内明明有 `contract-review` 且
BM25 排名第一，只是被关系图扩展补入的候选稀释了归一化分母）。

**因此改用 BM25 原始分**（TF-IDF 累加值，量纲固定、跨查询可比）作为分流信号。

### 阈值标定（实测，42 条查询）
| 查询类型 | BM25 原始 top-1 分布 |
|---|---|
| 真实科研任务 dev（20 条） | 9.9 – 88.9（中位 42.6） |
| 真实科研任务 heldout（12 条） | 20.7 – 61.8（中位 33.7） |
| 交付物任务（5 条） | 8.0 – 29.0 |
| 无关问题（5 条） | 0.0 – 4.6 |

### 一个被实测纠正的错误（记录在案）
初版阈值取 6.0（落在两组边界 4.6 / 8.0 之间），但实测发现 dev 集里两条真实任务
（「省级面板数据评估产业政策」raw=3.80、「农田耕作方式对产量影响」raw=4.27）
会因此**被误判为「无匹配」**——这是最不能接受的错误类型（误杀技能）。

改为**保守标定**：只有词面几乎完全不重叠（`raw < 2.0`）才判无匹配，其余一律建议确认。
设计原则：**错杀技能的代价 > 多问一句的代价**。

最终判据：
| 分档 | 判据 | 下游动作 |
|---|---|---|
| 可自动执行 | BM25 原始分 ≥ 15 | 直接进入编排与执行 |
| 建议确认 | 2 ≤ 原始分 < 15 | 展示候选，人工确认后执行 |
| 无匹配 · 直答 | 原始分 < 2 | 交给通用模型，不硬套技能 |

### 验证
- **32 条真实任务（dev 20 + heldout 12）零误杀**
- 5 条无关查询中 4 条判为直答，1 条（「推荐一部电影」raw=4.64）判为建议确认——可接受
- 新增 5 项 pytest 锁定该行为契约（无关查询不得 auto、真实任务不得 direct、
  阈值边界稳定、confidence 单调有界、分流不改变检索结果）

### 已接入的展示
- `/api/search` 与 `/api/demo` 返回 `confidence` / `raw_bm25_top` / `fusion_score` /
  `decision` / `decision_reason`
- 汇报演示页检索阶段显示分档徽章（可自动执行 / 建议人工确认 / 无匹配 · 直答）
- 说明文档新增 2.5 节

## 三、Nexus 代码分析结论

### 它的核心算法资产（按价值排序）
1. **三阶段规划**（`core/planner.py`，860 行）：任务分解（只拆子任务、标注交付物形态、
   禁止选技能）→ 子任务级向量检索（每子任务 Top-4）→ 候选内选择题式绑定。
   职责分离解决「一次调用既拆任务又选技能导致偷懒合并」的问题。
2. **防幻觉降级矩阵**：需求校验 → 技能 id 白名单过滤（幻觉 id 剔除并记录）→
   检索 Top-1 兜底 → 通用模型直答。**层层降级但绝不阻断主链路**。
3. **动态 Token 预算四档**（brevity/simple/rich/complex）：按 Planner 打的复杂度标签分派
   `max_tokens` 与 `reasoning_effort`，含「空正文重试」——预算是「思考 + 正文」总和，
   空正文时翻倍封顶 65536 并降思考档位，把预算真正留给正文。
4. **执行指纹缓存**（`core/cache_store.py`）+ 任务记忆向量存档（`task_{id}_queries` 集合）。
5. **附件直传**：pdf/xlsx/pptx/docx/txt/md/csv 上传后供技能执行，任务结束即删（生命周期铁律）。
6. **3D 技能网络可视化**（`frontend/components/skill_net_3d.py`，1295 行）：
   Three.js 深空星云 + 执行路径动画（Focus → Extract → Link → Flow → Ripple）+
   **三层降级**（3D → ECharts 2D → 纯 CSS，20 秒看门狗）。

### 实跑测试结果
在隔离环境（`~/.workbuddy/binaries/python/envs/default`）安装依赖后：

```
153 passed, 1 error in 30.09s
```

- 首次运行 136 passed / 14 failed（缺 python-multipart 与 streamlit）
- 补齐依赖后 **153/154 通过**
- 唯一 error：`test_docgen.py::test_output_dir_anchor` 断言
  `"Skill Agent" in os.path.dirname(ORIG_OUT)`——即**把测试绑定到作者本机桌面的目录名**，
  换机器/换解压位置必然失败。属测试可移植性问题，非功能缺陷。
- **给成员的反馈**：该断言建议改为「相对锚点」判断（如断言路径以项目根为基准、
  或通过 `NEXUS_OUTPUTS_DIR` 注入），否则 CI 与同事机器上会长期红灯。

### 与我们架构的对齐点（已确认无需改动）
- 防幻觉的技能 id 白名单：我们的 `orchestrator.build_from_relations` 已做等价校验
  （LLM 返回的依赖边只保留双方都在候选池内的）。
- 降级可观测：我们在 v0.3 已实现（`degraded` / `components` / `degraded_reason`），
  与 Nexus 的降级矩阵哲学一致。

## 六、已知边界（诚实说明）

1. **技能扩容后未重跑 dev / heldout 实验**。现有实验数据（检索召回、编排完整度、
   执行评分）都是 51 技能 / 62 条边条件下的结果，与当前 75 技能 / 90 条边的库
   **不是同一实验条件**。文档中的实验章节已显式标注该条件未更新——
   这是刻意的：改数字等于篡改实验前提。
2. **导入技能的契约字段是「提炼」而非「作者确认」**。practices、verification 等字段
   由转换脚本从原文提取，可能不如原始 51 个技能精细；技能正文已注明来源与复核要求。
3. **分流阈值的样本量有限**（42 条查询）。当前采用保守口径规避误杀，
   更大规模标定需要更多标注查询。
4. **Nexus 的真 embedding 检索未接入**（无智谱 key），我们的离线检索在
   「措辞差异大」的查询上相关度估计仍偏弱——这正是保守阈值的另一个理由。
