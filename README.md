# SkillNet-S1 · 立理 S1 科研技能生态原型

> 给 s1.liliai.cn 的 Agent 与 300+ 科研工作流之上补一层**技能运维层**：
> 技能被组织成网络、被检索路由、被选择性评估、并持续进化。
> 本 demo 用来判断这条路是否走得通，以及该怎么接进立理 S1。

## 零、快速开始

### 环境要求

- **Python 3.10 或更高**（唯一的硬性依赖）
- 首次运行需要联网（自动安装 5 个 Python 包）
- 可选：Node.js（仅用于跑前端渲染自检 `tools/front_check.js`）

### 启动（二选一）

**Windows** — 双击 `start.bat`

**macOS / Linux**

```bash
bash start.sh
```

脚本会自动完成四件事：挑选合适的 Python 解释器 → 检查并安装缺失依赖 →
检查模型密钥（可选）→ 启动服务并打开浏览器。全程有中文提示，出错会告诉你怎么办。

服务地址 `http://127.0.0.1:8848`，**关闭命令行窗口即停止**。

### 没有模型密钥也能用

绝大部分能力不依赖大模型，开箱即可体验：

| 不需要密钥 | 需要 `DEEPSEEK_API_KEY` |
|---|---|
| 技能库浏览与检索对照（三档策略并排对比） | Fabric 任务级路由与依赖编排 |
| 技能关系图（51 节点 / 62 条边的交互式可视化） | 技能驱动的研究 Agent 执行与盲评 |

| 跨框架导出（Claude Code / ADK / OpenAI / 索引） | 一键全链路演示 |

需要密钥时：把 `.env.example` 复制一份改名为 `.env`，填入 `DEEPSEEK_API_KEY` 后重启
（`start.bat` / `start.sh` 首次运行会自动帮你复制这份模板）。用的是 DeepSeek 开放平台，
按量计费，跑完本项目的全部实验约 ¥5。

### 可选：接口访问令牌

默认不启用（本地演示足够）。如果要把服务跑在**别人也能访问到的机器上**：

## 一、为什么做这件事：三个来自文献的事实

| 事实 | 出处 | 对我们的含义 |
|---|---|---|
| 前沿 Agent 在真实大技能池上的**技能检索与编排能力极弱**。SkillNet-Gym 中检索完整度只有 8%–39%，一旦要求把检索到的技能组织成依赖保持的工作流，硬任务分数进一步崩塌 | SkillNet, arXiv:2603.04448, 表 3 | S1 已经有 300+ 工作流与数百 Skills。**技能变多之后，"找对技能"本身就是瓶颈**，这是我们的机会点 |
| 技能优化**不必逐轮重写**。用上下文老虎机分配评估预算、周期性做种群更新，在六个基准上取得最高平均分，优化成本比 SkillOpt 下降 55%–58% | COBRA-Skills, arXiv:2609.11682 | 技能库的维护成本是可控的，**可以做成常驻的后台优化任务** |
| 把仓库与论文蒸馏成**操作性知识**（而非复述答案）后，同一个 research agent 在 MLE-bench 上分数提升 **134.3%**，而模型、harness、执行预算全部固定 | DisCo / Repo-To-Skill, arXiv:2609.02749 | **技能是独立于模型能力的变量**。S1 换模型不用重做技能层，技能层反过来对所有模型都有效 |
| 另外：社区评测（Vercel agent evals）发现默认配置下技能在 56% 的测试用例里**根本没被激活** | adk.dev / agentpatterns.ai | 光有技能库不够，**必须有一层负责"什么时候该用哪个技能"**——这正是本原型填补的位置 |

一句话：**S1 需要的不只是一个技能库，而是一个会挑选、会评估、会自我更新的技能中枢。**

## 二、Demo 做了什么

```
seed/catalog_data.py   51 个真实科研技能（17 个领域，按 agentskills.io 规范）
        │
        ├─ skillnet/schema.py      技能数据模型：技能卡 / 类型化关系 / 五维质量
        ├─ skillnet/catalog.py     技能库：构建、去重、持久化、SKILL.md 导出
        ├─ skillnet/index.py       BM25 + 稀疏语义向量 + 加权融合
        ├─ skillnet/retriever.py   混合检索 → 关系扩展 → LLM 重排（Fabric 式）
        ├─ skillnet/orchestrator.py 依赖保持的技能工作流编排
        ├─ skillnet/bandit.py      LinUCB 上下文老虎机（技能选择）
        ├─ skillnet/evolver.py     蒸馏 / 变异 / 交叉 / 再生成 + 准入过滤
        ├─ skillnet/agent.py       技能驱动的研究 Agent
        ├─ skillnet/judge.py       独立盲评（rubric + 客观要点覆盖率）
        └─ skillnet/adapters.py    Claude Code / Google ADK / OpenAI Tools 导出
```

### 1. 技能本体（SkillNet 三层结构的落地）

每个技能不是一段 prompt，而是一个结构化资产：

- **技能卡（Skill Contract）**：能力 / 输入 / 输出 / 适用时机 —— 检索时只读这一层，不读全文
- **类型化关系图**：`depend_on`（前置依赖）、`compose_with`（常被共同调用）、`similar_to`（可替代）
- **五维质量评估**：安全性、完整性、可执行性、可维护性、成本感知

### 2. 三档检索策略（可对照、可消融）

| 档位 | 做法 |
|---|---|
| `bm25` | 纯关键词检索（朴素基线） |
| `hybrid` | BM25 + 语义向量 + 领域/标签结构信号，加权融合（BM25 0.55 / 语义 0.30 / 结构 0.15）+ 多路一致性加成 |
| `fabric` | 在前者基础上做**关系图扩展**（沿依赖/组合边补入工作流上下游）+ **LLM 重排**（以技能卡为输入） |

### 3. 强化学习：LinUCB 上下文老虎机

> 优先级 = **预测收益** + **探索奖励**
> `priority = θᵀx + α·√(xᵀA⁻¹x)`

- 上下文 `x` 来自技能的语义表示 —— 因此**一次评估的反馈能影响语义相近的未评估技能**
- 最终输出按**实测平均奖励**选取，不按预测分数（与 COBRA-Skills 一致）
- 消融对照：`random` 选择器（保留进化、去掉老虎机）

### 4. 技能进化闭环

| 算子 | 输入 | 作用 |
|---|---|---|
| `distill` | 一次真实执行轨迹 | 提炼可迁移的操作性知识（DisCo 路线） |
| `mutate` | 某技能的成功/失败轨迹 | 局部修补（COBRA 的 rollout mutation） |
| `crossover` | 两个高分技能 + 低分技能作负面证据 | 有依据的借鉴，不做文本拼接 |
| `regenerate` | 无技能轨迹 + 任务类型 | 打开新搜索方向 |

**准入过滤**（对应 SkillNet 的防污染）：技能名合规 → 步骤数 ≥3 → 与现有技能 Jaccard 相似度 < 0.72 → 才允许入库。

### 5. 跨框架接入（组长点名的需求）

已核实：Google ADK 自 v1.25 起通过 `SkillToolset` 支持 Skills，遵循 **agentskills.io** 目录规范，
官方文档明确说明「为 Claude Code / Cursor / Gemini CLI 编写的技能目录可用 `load_skill_from_dir` 原样加载」。

因此本项目的 `SKILL.md` 目录是**唯一真源**，一次导出四份产物：

| 目标 | 产物 |
|---|---|
| Claude Code / Cursor / Gemini CLI | `.claude/skills/<name>/SKILL.md` + `CLAUDE.md` 激活提示 |
| Google ADK | `skills/<name>/SKILL.md` + 可直接运行的 `agent.py`（`SkillToolset`） |
| OpenAI function calling | `tools.json`（`search_skills` / `load_skill` 两级渐进披露）+ `skill_index.json` |
| 对照方案 | `SKILLS_INDEX.md`（压缩文档索引，用于对照"技能是否被激活"） |

## 三、生产化加固（v0.2）

第一版是可运行原型。这一版按「要接进生产」的标准做了一轮加固 ——
下面每一条都对应一个**真实存在的缺陷**，不是纸面上的最佳实践。

### 3.1 修复的缺陷

| 缺陷 | 真实后果 | 修法 |
|---|---|---|
| **技能库完全没有持久化** | `/api/evolve` 新增的技能、老虎机回填的实测奖励，**重启即全部丢失**；`catalog.py` 里的 `save/load` 写好了却从未被调用 | 接线持久化，原子写入（临时文件 + `os.replace`）。落盘只写「演化技能 + 运行统计」，种子技能由代码提供 —— 这样升级代码时种子更新能自动生效，演化成果也不会丢 |
| **全局状态无锁 + 索引就地重建** | 并发下抛 `RuntimeError: dictionary changed size during iteration`；更隐蔽的是「新技能名配旧向量矩阵」，**静默返回根本不存在的技能** | 技能库加可重入锁、遍历方法返回副本；索引重建改为「局部构建 + 一次性赋值」（Python 属性赋值是原子的）；运行时对象整体替换而非就地改 |
| **用内置 `hash()` 做向量哈希** | Python 对字符串的 `hash()` 受 `PYTHONHASHSEED` 影响，**每个进程都不一样** → 索引不可复现、不可持久化、历史检索结果无法回溯 | 换成 CRC32，跨进程 / 平台 / 版本稳定 |
| **成本账本是全局单例且每请求 reset** | 并发下每个请求返回的成本数字都是错的（A 的账单里混进 B 的用量）；且 `run_cost + LEDGER.cost_yuan` 两处相加，**重复计费** | 用 `contextvars` 实现请求级账本，作用域外自动回落到全局账本（脚本与实验继续沿用） |
| **付费接口零鉴权** | 一旦用 `--host 0.0.0.0` 暴露到内网，任何人都能无限刷 API 额度并污染技能库 | 支持 `SKILLNET_TOKEN` 环境变量；启用后，消耗额度与写盘的接口要求 `X-SkillNet-Token` 头（用 `secrets.compare_digest` 比较，防时序攻击） |
| **`requirements.txt` 漏了 numpy** | 照清单装完依赖后，`verify.py` 与实验脚本直接 ImportError | 补上 |
| **非法参数返回 500** | 模式名传错就直接炸，使用者不知道错在哪 | 请求模型全部加 Pydantic 校验（枚举白名单、长度上下限），返回 422 与中文说明 |
| **进化技能的质量一律写 Average** | `quality_score()` 的质量先验退化成常数，**检索排序里的质量加权形同虚设** | 新增启发式五维评估，每个维度给出「等级 + 理由」；安全性评为 Poor 的技能直接拒收 |
| **编排遇环静默出错** | 三人以上的环会让节点被丢到拓扑序列末尾，给出**违反依赖关系的执行顺序却没有任何提示** | 显式打断环，并在返回结果里回报 `cycles_broken` |
| **无日志** | 生产环境不可观测 | 全仓接入 `logging`，级别可用 `SKILLNET_LOG_LEVEL` 调整 |
| **路径穿越风险** | 技能名被直接当目录名使用（演化技能来自模型输出，落盘后又被读回） | 导出前做白名单校验 |

### 3.2 对齐 agentskills.io 官方规范

对照规范原文逐条核对后，补齐了几个第一版遗漏或没利用上的点：

- **补上可选 frontmatter**：`license`、`compatibility`（环境要求，如「Python 3.10+，需要网络」）、
  `metadata`（自定义键值）、`allowed-tools`（实验性）。
  价值在于跨团队分发：接收方一眼能看出这个技能需要什么环境、什么许可、由谁产出。
- **正文预算**：规范建议正文 ≤ 500 行 / 约 5000 token，超出部分拆到 `references/` 按需加载。
  本项目技能正文实测 52–58 行 / 约 400–450 token，留有余量；自检已加这一项。
- **name 必须与所在目录名一致**且符合 kebab-case —— 已加入校验。

### 3.3 跨框架导出的一处关键修正

第一版只导出了 `.claude/skills/`，隐含假设是「一份目录走遍天下」。
调研后发现：**文件格式确实统一，但各家去哪个路径找技能并不一样**。

| 客户端 | 技能目录 |
|---|---|
| Claude Code | `.claude/skills/` |
| Codex | `.agents/skills/` |
| Cursor | `.cursor/skills/` |
| Gemini CLI | `.gemini/skills/` |

现在一次写全四个落点，并额外生成仓库级 `AGENTS.md`（把技能索引直接放进 agent 上下文 ——
调研显示这种做法在部分评测里比技能机制更可靠地触发调用）。

### 3.4 自检从 21 项扩到 29 项

新增的全部是生产化检查，且每一项都能独立复现：

| 检查 | 验证方式 |
|---|---|
| 规范符合性 | name / description / 正文预算逐条核对 |
| 持久化往返 | 落盘 → 重新加载 → 比对技能集合与运行统计 |
| **检索索引跨进程可复现** | 用两个不同的 `PYTHONHASHSEED` 起子进程，比对向量指纹是否一致 |
| **并发读写安全** | 2 个写线程 + 4 个读线程并发 2 秒，断言零异常、零幽灵技能 |
| **成本账本请求级隔离** | 两个作用域分别记账，断言互不串账且作用域外回落到全局账本 |
| 导出路径安全 | 路径穿越 / 大写 / 超长 / 含空格名必须全部被拦截 |
| 编排环可观测 | 打断环后拓扑序仍然合法，且返回 `cycles_broken` |
| 质量评估带理由 | 五维均含 level 与 reason；危险操作必须评为 Poor |

## 五、实验结果

> 全部指标由 DeepSeek API 真实执行产生，非模拟数据。原始结果见 `out/exp*.json`。

### 实验一 · 技能检索与编排

**设置**：20 个科研任务，从 51 个技能的库中检索 K=5 个技能。金标准（gold）为人工标注的「完成任务所必需的技能集」与技能间依赖边。

| 检索策略 | 技能召回 | 完全覆盖 | 编排完整度 |
|---|---|---|---|
| BM25 关键词 | 77.5% | 50.0% | 60.0% |
| 混合检索（+语义+结构） | 78.3% | 55.0% | 62.5% |
| **Fabric 完整方案**（+关系扩展+LLM 重排） | **95.8%** | **90.0%** | **92.5%** |

**读法**：

- 关键词检索能命中大部分技能，但**只有一半任务能凑齐完整的技能集** ——
  漏掉的那个技能往往正是让任务跑通的关键（例如单细胞任务里漏了 `differential-expression`）。
- **关系图扩展是提升最大的一环**：完全覆盖率从 55% 跳到 90%。
  这印证了 SkillNet-Fabric 的核心主张 —— 在大技能池里，光靠「和查询像不像」不够，
  还要沿技能间的依赖与组合关系把工作流上下游补齐。
- **编排完整度从 60% 到 92.5%** 说明：技能集选对了，执行顺序基本能自动推出来。
  而这依赖**技能关系图的边是有方向的**（构建期做了一次关系规范化 + 人工方向定标，
  见 `skillnet/catalog.py::normalize_relations`）。
- **融合权重是扫描标定过的，不是拍脑袋定的**：早期用 0.55/0.30/0.15 时，
  混合档的召回反而**低于**纯 BM25 基线（76.7% < 77.5%）——
  因为本环境的语义通路是稀疏向量的降级实现，噪声偏大。
  扫描后取 0.70/0.20/0.10，混合档稳定优于基线。
  **这个权重在接入稠密编码器后需要重新标定。**

### 实验二 · 技能对执行质量的影响

**设置**：12 个任务 × 4 档技能供给 × 3 次重复取均值。评审为 LLM 盲评（不知道方案来自哪一档）。

| 技能供给方式 | 盲评均分 | 领域要点覆盖率 | 技能采纳率 | 相对基线 | 成本/任务 |
|---|---|---|---|---|---|
| 无技能 | 8.22 | 81.3% | — | 基线 | ¥0.051 |
| 仅技能卡（L1 元数据） | 8.52 | 88.0% | 89.4% | +3.6% | ¥0.063 |
| 混合检索 + 技能全文 | 8.79 | 90.6% | 65.6% | +7.0% | ¥0.065 |
| **完整方案**（关系扩展 + 重排 + 全文） | **8.86** | **92.8%** | 88.9% | **+7.8%** | ¥0.074 |

四档在**评分与覆盖率两个维度上都严格单调递增** —— 技能供给越充分，方案越好，这不是巧合。

配对比较（同一任务内对比无技能基线，消除任务难度差异）：
仅技能卡 8 胜 1 平、混合检索 9 胜 2 平、**完整方案 9 胜 2 平**，覆盖率 7 胜。

**这个结果比「提升了多少分」更重要，它给出了三条结论：**

1. **技能的真实价值主要体现在「专业操作要点的覆盖」。**
   要点覆盖率从 81.3% 提升到 92.8%（**+11.5 个百分点**），而盲评均分提升 7.8%。
   原因是有明确对错的专业细节（线粒体阈值按组织分别设定、留元外推怎么切分、
   平行趋势检验怎么做……）本来就该被写进方案，而 LLM 打分对这类
   「该有的有没有」并不敏感 —— 它对文风与篇幅的反应要大得多。
   **这正是 SkillNet 论文坚持用「能不能跑通 unit test」而不是让 LLM 打分的原因**，
   也说明把评估推进到产物级是必要的，而不是可选的。

2. **存在明显的天花板效应。** 无技能基线已经拿到 8.22/10 —— 任务本身是「给出研究执行方案」，
   而 DeepSeek 在通用科研方法论上本来就很强。技能补的是**特定工具的具体用法与陷阱**，
   这份增益在「方案级」任务上被压缩了。SkillNet 论文也报告过同样的现象：
   「easy tasks 的改进空间有限，hard tasks 受益更明显」。

3. **技能采纳率是一个被普遍忽视的指标。** 即使把技能全文摆到 Agent 面前，
   也平均只有 66%–89% 的技能被真正写进方案。这与社区评测的发现方向一致
   （Vercel agent evals：默认配置下技能在 56% 的用例中从未被激活）。
   **「技能没被激活」是独立于「技能质量」的问题**，必须单独度量与优化。

> 关于数字的稳定性：本轮加固更换了向量哈希方案（内置 `hash()` → CRC32），
> 因此向量分布发生变化，实验二重新跑过一遍。加固前后两轮的结论方向完全一致
> （四档单调、完整方案领先、覆盖率增益大于评分增益），只是绝对数值有 1–2 个百分点的浮动。

### 实验三 · 老虎机选择与技能进化闭环

**设置**：6 轮优化循环，两组使用同一份种子技能库。每轮由选择器挑一个技能、真实执行并盲评打分，
得分回流更新选择器；偶数轮触发一次技能蒸馏。

| 选择策略 | 平均实测奖励 | 最佳技能 | 技能库规模 | 蒸馏出的新技能 | 成本 |
|---|---|---|---|---|---|
| LinUCB 老虎机 | 0.802 | literature-review (0.900) | 51 → 54 | 3 | ¥0.145 |
| 随机选择（消融） | 0.819 | deep-learning-training (0.900) | 51 → 54 | 3 | ¥0.146 |

**逐轮选择记录**：

| 轮次 | 任务 | LinUCB 选择 | 随机选择 |
|---|---|---|---|
| 1 | T01 单细胞 | `scrna-qc-clustering` | `data-cleaning` |
| 2 | T02 材料 | `dft-formation-energy` | `admet-prediction` |
| 3 | T03 文献 | `literature-review` | `deep-learning-training` |
| 4 | T04 临床 | `clinical-feature-engineering` | `leakage-guard` |
| 5 | T05 因果 | `econometric-panel` | `statistical-testing` |
| 6 | T06 对接 | `molecular-docking` | `admet-prediction` |

**怎么读这个结果 —— 这里有一个比数字更重要的发现**：

- **选择行为上的差异是清晰的、可复现的**：LinUCB 每一轮都选中了与任务领域直接对应的技能
  （单细胞→单细胞技能、材料→材料技能、文献→文献技能），
  而随机选择经常落到通用技能或邻域技能上（T02/T06 都选了 `admet-prediction`，
  T03 选了与文献无关的 `deep-learning-training`）。
- **但实测奖励上，两组不可区分** —— 而且这一点有硬证据：
  **同一份代码、同一批任务，两次独立运行给出了相反的结论**。
  第一次 LinUCB 0.831 > 随机 0.820，第二次 LinUCB 0.802 < 随机 0.819。
  差异都在 0.02 以内，方向却反了 —— 这就是噪声，不是效应。

  这个结果比「老虎机赢了 0.011」更有价值：它用实验说明，
  **在方案级评估上，选择策略的收益根本无法被测出来**。原因与实验二同源 ——
  任务存在天花板，且奖励信号的分辨率不足（所有配置都挤在 8.0–9.0 区间）。
- **真正的价值需要更长预算才能显现**。COBRA-Skills 用的是 30 轮 × 50 个样本；
  本 demo 的 6 轮只是**管线连通性验证** —— 它证明了闭环能跑通
  （选择 → 执行 → 回填 → 进化 → 再检索），而不是证明它能带来多少收益。
- **进化侧是确定生效的**：两组各自蒸馏出 3 个通过准入过滤的新技能
  （如 `composition-only-formation-energy-extrapolation`、
  `survival-modeling-with-ehr-features`、`sequence-to-lead-virtual-screening`），
  库规模 51 → 54，检索索引随之刷新，且这批技能已能落盘、重启不丢。

**结论**：管线可行、成本可控（整个优化循环不到 ¥0.15），
但**要证明强化学习选择的价值，必须换到「有唯一正确答案、可自动判分」的任务集上做**。
本实验的最大产出不是那 0.802 与 0.819，而是「两次运行结论相反」这个事实本身。

## 六、怎么接进立理 S1

按侵入性从低到高，三条路径，**可以分阶段推进，每一阶段都能独立验证收益**：

### 路径 A · 轻量：只替换技能路由层（1–2 周）

保持 S1 的 Graph Engineering 图与执行器不动，只在**技能选择**这一步插入本原型的检索链路：

```
用户任务
   ↓
[SkillNet 检索层]  BM25 + 语义 + 结构 → 关系扩展 → LLM 重排
   ↓  输出技能卡（不是全文，控制上下文）
S1 现有调度器：选 workflow → 图节点执行
```

- **收益**：解决"技能没被激活"与"选错技能"两类问题，上下文占用下降
- **风险**：低。检索层无状态，可灰度、可回退
- **验证**：在 S1 已有的真实 case 上做 A/B，看技能命中率与任务返工次数

### 路径 B · 中度：技能库接入进化闭环（1–2 个月）

把 S1 每次任务的**执行轨迹**沉淀下来，离线跑进化算子：

```
S1 执行轨迹 ──► 蒸馏 / 变异 ──► 准入过滤 ──► 候选技能池
                                              ↓
                                    人工评审 / 影子评估
                                              ↓
                                       S1 正式技能库
```

- **收益**：技能库从"人工维护"变成"越用越厚"，且新知识来自真实执行而非想象
- **关键**：准入过滤不能省（SkillNet 明确指出技能库会被污染），必须有人工或强评审兜底
- **验证**：统计新增技能被后续任务真实调用的比例与带来的分数变化

### 路径 C · 深度：老虎机嵌入调度器（探索性）

把 S1 的 Graph Engineering 图节点（或 workflow）视为**臂**，用 LinUCB 决定"下一个执行哪个节点/工作流"：

- 状态 `x`：当前研究上下文 + 候选技能/工作流的语义表示
- 奖励 `r`：该节点的实际贡献（评审分数、产物是否被后续步骤采纳、是否返工）
- 好处：**用户的使用过程本身就是训练数据**，调度策略随使用自动变好
- 风险：奖励设计是难点；建议先做离线回放（用历史 case 的日志做 off-policy 评估）再上线

### 建议的落地顺序

```
路径 A（检索层）→ 验证 → 路径 B（进化闭环）→ 验证 → 路径 C（调度 RL）
        ↑ 每阶段都有独立可测的收益，任何一步不成立都可以停在这里
```

## 七、局限与下一步

**本原型诚实声明以下局限：**

1. **语义检索用的是稀疏向量而非稠密编码器**。demo 环境无法下载 HuggingFace 模型，
   故语义通路用「词级 IDF 加权 + 余弦相似度」近似，配合 LLM 重排补足。
   SkillNet 论文中 BM25 → 稠密检索（BGE/Qwen3-Embedding）有约 24 个百分点的差距，
   **接入稠密编码器后检索指标还有明确上升空间**（`VectorIndex` 接口已预留）。
2. **技能库是 51 个手写种子技能，不是 60 万级**。规模远小于生产技能库，
   检索难度因此偏低 —— 真实场景下技能池越大，本原型的相对收益应该越明显。
3. **执行是"方案级"而非"真跑代码"—— 这是最关键的局限。**
   实验二与实验三都出现了明显的**天花板效应**：无技能基线已经拿到 8.32/10，
   LinUCB 与随机选择的差距只有 0.011。这说明在"给出研究执行方案"这类任务上，
   强基线模型本身就很强，技能的增量被压缩。S1 已有沙箱与独立评审，
   **接入后可以做「真跑代码 + 产物校验」的评估，那是能真正分离出技能增益的场景**。
4. **评审是 LLM 单评判**，会引入噪声。因此实验二额外用了**客观要点覆盖率**与
   **技能采纳率**两个不受评审影响的指标做交叉验证；生产环境应做多评判投票或人工抽检校准。
5. **未做跨模型迁移实验**。COBRA-Skills 图 6 的结论（36 组非对角迁移中 34 组正收益）
   提示技能在模型间可复用 —— 这对 S1 多国产模型并存的架构非常有价值，值得单独验证。

**下一步优先级（按"能多快拿到可信结论"排序）：**
1. **打通真实沙箱执行，把评估从"方案级"提到"产物级"**。这是解除天花板效应、
   让实验二与实验三的结论真正有区分度的前提，也是接进 S1 后最容易做到的
   （S1 的沙箱与评审机制已经就位）。
2. **接入稠密编码器**，重跑实验一（成本最低、收益最确定，预期还有 10+ 个百分点的空间）。
3. 把 S1 真实 case 转成评测任务集，用 S1 自己的执行日志做 gold 标注 ——
   届时任务难度会自然上升，天花板效应随之减弱。
4. 做跨模型迁移验证（技能在 Kimi / Qwen / GLM / DeepSeek 之间是否可复用）。

## 九、怎么确认它能跑

```bash
python verify.py          # 29 项组件级自检，不需要 API key
python verify.py --llm    # 额外跑真实检索 / 蒸馏 / 评审链路
node tools/front_check.js # Dashboard 渲染自检（需先 node，检查 SVG 生成与格式化函数）
```

`verify.py` 分六大类共 29 项：

| 分类 | 检查内容 |
|---|---|
| 技能库与本体 | 命名与描述合规（agentskills.io 规则）、去重、关系图无悬空引用、SKILL.md frontmatter 合法、可执行步骤完整 |
| 索引与检索 | BM25 与向量检索命中正确文档、加权融合顺序正确、三档检索可运行 |
| 强化学习与进化 | LinUCB 选择与探索奖励衰减、消融选择器、准入过滤、拓扑排序、环检测与打断、编排环可观测、质量评估带理由 |
| 跨框架导出 | 四客户端落点齐全、导出路径安全、种子目录落盘 |
| 评测集 | gold 引用有效、客观要点可抽取 |
| **生产化检查** | 规范符合性、持久化往返、**检索索引跨进程可复现**、**并发读写安全**、**成本账本请求级隔离** |

**自检抓出过的真实问题** —— 记录在此，说明它不是走过场：

第一轮（原型阶段）：
1. 编排器用无向邻居推导依赖边，把「A 依赖 B」反向记成「B 依赖 A」，拓扑序把下游排到上游之前
2. 准入过滤只用 Jaccard 相似度，漏掉了与现有技能高度重合的冗余技能
3. 融合排序缺一致性加成时，混合检索一度**低于**纯 BM25 基线

第二轮（生产化加固，对应第三节）：
4. `requirements.txt` 漏 numpy —— 照清单装完依赖后自检直接 ImportError
5. 用内置 `hash()` 做向量哈希 —— 换两个进程跑，同一份技能库编出的向量都不一样
6. 技能库的 `save/load` 写好了却从未被调用 —— 进化成果重启即丢
7. 索引就地重建会在并发下让检索**返回不存在的技能名**（静默错误，最难发现）
8. 成本账本全局单例 + 每请求 reset + 两处相加 —— 并发下账单错乱且重复计费
