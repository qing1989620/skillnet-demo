# 第一阶段评分锚点 v2

版本日期：2026-11-05。用途：固定版本、完整材料包的可观察质量评价。开发规格，尚无双人独立标注校准结果。它是研究操作定义，不是官方认证标准。

## 使用规则

评审单位是一个固定版本的 Skill 包，包括 SKILL.md 及其登记资源，不是名称、搜索卡片或单段简介。先确定任务类型、适用材料和检查范围，再逐维评分。每个已评分维度需要：具体结论、证据定位、反证/缺口、评分锚点和评审者身份。

- `unknown / score=null`：材料不可得、专业能力不足或证据冲突无法裁定；不能补成 0、2 或“平均”。
- `not_applicable / score=null`：该维度确实不适用，必须说明理由。例如纯咨询 Skill 不要求附带可执行脚本，但仍需可遵循的操作程序。没有脚本本身不能扣分。
- `0–4`：只在材料可检查且维度适用时使用。确认缺失与未获得材料不同。高分表示相应文档/实现属性有充分支持，不表示任务成功概率为 100%。
- 缺失项严重性须按任务契约判断：安全关键前提不明可能是重大缺陷，普通建议的可选示例缺失不能同等扣分。相同缺陷可涉及多维，但记录同一 finding_id，不能把多维命中当作多个独立问题。
- 正向与反向证据同时出现时写明冲突，不能挑有利片段；正好落在两档之间取较低且有完整支持的一档。不同评审的分歧先保留，再独立仲裁。
- 八维分别报告；不默认求总分。安全、完整性、许可门禁单独裁定，不能用其他高分抵消。
- 本地哈希与许可证文本只能证明材料一致和有何声明；不能独自证明上游真实身份、全部权利链或法律适用性。

## 1. 契约一致性 contract_consistency

问题：声明的能力、步骤、资源实现、产出和限制是否一致？

0. 关键承诺被可定位实现直接否定，或遵循主流程会产生与目标相反的结果；需确认上下文与替代路径。
1. 存在影响主要结论的实质冲突，且未明确限定。例如把常数默认项解释为真实测量结果。
2. 主要流程方向一致，但输入/输出、适用条件或部分资源之间有未解释差异。
3. 主能力、输入、输出与主要资源可对应；重要限制明确，未发现实质冲突。
4. 正常、异常、边界与排除条件均可交叉定位；声明与实现/程序逐项对应，冲突处有明确处置。

扫描到冲突线索不直接给 0/1，必须核查它是否影响整个承诺、只是例子、或已在文档中限定。

## 2. 完整性 completeness

问题：读者能否知道需要什么、如何操作、产生什么、失败怎么办？

0. 缺失实现主要能力必需的步骤或资源，且无可用替代，主流程无法据此完成。
1. 有目标与零散步骤，但关键输入、依赖、资源、输出或失败处置存在重大缺口。
2. 输入—步骤—输出基本存在，异常、前提、恢复或边界有实质遗漏。
3. 主要输入、依赖、步骤、输出、常见失败和限制齐备，足以按声明条件开展操作。
4. 在 3 的基础上，边界情形、诊断、恢复与资源引用完整对应，关键决策无需猜测。

按所需信息评分，不能按字数、步骤数、图片数评分。

## 3. 静态可操作性 static_executability

问题：文档是否能被具体地遵循？此处不测真实执行成功。

0. 已确认关键命令、路径或接口不可用且无替代，或程序指令存在阻断性矛盾。
1. 关键步骤需大量猜测；接口、依赖、必需资源或具体操作规则不充分。
2. 主操作具体，但环境版本、参数含义、路径、状态转换等有实质歧义。
3. 操作型 Skill 有足够明确的环境/接口/参数；咨询型 Skill 有可遵循的决策规则及输入输出要求。
4. 在 3 的基础上，前提、兼容范围、失配诊断和替代路径可交叉检查，关键接口无已知静态冲突。

AST 中找到了 CLI 参数，只支持“静态存在该参数”；不能支持“命令成功”“参数值正确”或“没有危险副作用”。

## 4. 验收设计 verification_quality

问题：Skill 是否提供能发现错误的验收，而不是让自己宣布成功？

0. 验收规则明确会接受已知关键错误，或用自报高分替代必需事实核验。
1. 仅说“检查正确”“审阅结果”，或主要依赖未经说明的自评指标。
2. 有具体检查，但缺少部分关键指标、独立参照、错误样例或可判定容差。
3. 关键产物、成功/失败条件和独立参照明确，检查原则上可由第三方执行。
4. 在 3 的基础上，包含正常、边界、错误对照及明确容差/版本；验收设计能覆盖主要失效模式。

这是对验收设计的评分。验收器实际运行结果、变异测试记录和 Skill 任务通过率另存，不能混写。

## 5. 可维护性 maintainability

问题：依赖变化、故障和版本更新后，能否定位与修复？

0. 已确认不可恢复的关键依赖/版本冲突，且无诊断或替代。
1. 依赖、版本、故障诊断或更新方式大多不明。
2. 有部分模块划分、版本/依赖说明或常见故障处理，但不系统。
3. 主要依赖与兼容条件可追踪，常见故障有诊断与替换/更新办法。
4. 在 3 的基础上，版本迁移、变更验证、回滚或兼容检查形成明确程序。

仓库星数、图中节点度、作者名气不属于本维证据。

## 6. 来源与许可证据 provenance_license

问题：能否查明这份材料来自哪里、是哪一版、有哪些许可声明？不代替法律意见。

0. 已确认来源/完整性伪造，或已确认使用方式与明确许可限制冲突。
1. 只有无法交叉核对的来源/许可声明，关键组件归属不明。
2. 上游路径、固定版本、文件指纹及许可文本部分或全部可查，但组件覆盖或权利链仍有缺口。
3. 主要组成的固定来源、指纹、许可与署名要求均可追踪，未发现相互冲突的许可声明。
4. 在 3 的基础上，组件级许可清单和本研究具体使用/发布方式均经过有记录的合规复核。

许可证文件不存在但整个包可见，是可观察缺口；包根本无法获得则是 unknown。禁止仅凭“MIT”字符串给 4。

## 7. 成本意识 cost_awareness

问题：使用者能否预期并限制时间、算力、存储、调用量和费用？

0. 主流程存在已确认的无界重试/资源增长等严重问题且没有终止条件。
1. 有潜在重大资源开销，几乎未说明预算或终止条件。
2. 提到缓存、清理、分批、重试限制等部分措施，但重要预算仍未明确。
3. 主要资源有数量/时间/存储/调用边界及可操作的终止条件。
4. 在 3 的基础上，有测量、超限处理、费用核对或成本—质量折中方法。

资源生命周期 Skill 可以凭清理设计获得部分支持；不能因此声称它实际省了多少钱。纯本地任务不强求美元报价。

## 8. 安全边界说明 safety_documentation

问题：文档是否明确权限、信任边界、外部 I/O 和风险处置？

0. 文档明确要求绕过关键授权或保护边界，且不是被标注的反面教材；需独立安全裁决确认上下文。
1. 有高风险操作但基本未约束输入、权限、范围或恢复。
2. 有部分权限/输入/路径/外部数据限制，但重要攻击面或失败处置不充分。
3. 主要风险有明确最小权限、范围限制、失败处置和人工升级规则。
4. 在 3 的基础上，信任边界、注入/越界情形、拒绝条件、日志与恢复步骤均具体可核查。

`risk: safe` 是作者自述。包含 vulnerable/danger 字样可能是在讲反例。安全文档 4 分也不是“无恶意”认证。

## 独立于八维的门禁与最终判定

门禁分别记录 `pass / review / block / unknown` 及裁决者、范围、证据和时间：包完整性、授权许可、危险行为/注入、执行环境隔离。`block` 必须有已确认的阻断原因，扫描线索只进 `review`。本次三个案例均未完成独立人审，不发放 pass。

实际任务结果另记 `success / task_failure / timeout / infrastructure_failure / not_run`；边界预检另记匹配、前提不满足、未知、明确范围外、禁止动作。三者不能相互替代。任务增益只由同条件的有/无 Skill 对照测量，不能由八维平均分推出。
