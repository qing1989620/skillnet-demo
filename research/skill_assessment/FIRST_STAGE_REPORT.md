# 第一阶段：Skill 评价方法、能力边界与当前证据

日期：2026-11-05。研究对象：固定版本的单个 Skill。网络选择与编排优化留到第二阶段。

**本阶段要回答的是：这份 Skill 说自己能做什么，材料是否支持这种声明，在什么条件下适用，以及使用它是否让同一个 Agent 把任务做得更好。当前已完成方法规格、静态检查实现和三个真实案例的机制验证；尚未完成独立人类校准与真实任务对照，因此不能宣称评价准确率高或任务效果已提升。**

此前报告的重点是把项目跑通、冻结数据和核验旧结果。这些保证研究可以开始，不等于已经证明一个可信的 Skill 评估方法。下面只解释第一阶段的评价本身。

## 1. 我们究竟评什么

把一份写得漂亮的菜谱称为“可靠”，和证明照着它做出的菜符合要求，是两件需要不同证据的事。Skill 也是如此。

| 评价对象 | 要问的问题 | 什么证据能支持 | 当前进度 |
|---|---|---|---|
| 材料与实现质量 | 声明、步骤、资源是否完整且一致？ | 完整包审查、跨文件核验、独立人审 | 检查实现与案例已完成；人审未完成 |
| 能力边界 | 适合哪类任务、输入、环境、权限和预算？ | 明确契约 + 正常/边界/范围外任务 | 契约预检可运行；经验边界未测 |
| 实际任务价值 | 使用 Skill 是否比不使用更好？ | 同一 Agent 的有/无 Skill 配对试验，独立验收产物 | 尚未运行 |
| 安全与合法使用 | 是否有越权、恶意行为或使用限制？ | 独立安全/许可裁决、环境隔离和行为证据 | 线索与门禁已区分；未认证安全 |

因此，我们不把它们压成一个“95 分优秀 Skill”。文档清楚但实现有缺陷、一般文档但某类任务实测有效、材料不足、明确不适用，都应得到不同的结论。

## 2. 实际采用什么机制

采用“证据约束的分层评价”：固定版本 → 提取能力契约 → 文档与实现交叉核验 → 逐维判断并保留未知 → 独立复核 → 同条件真实任务试验。前四步已做出本地实现；后两步是必须补齐的效度验证，不能以模拟数据替代。

1. **固定评价对象。** 保存上游仓库、提交、原文路径、每个登记文件的 SHA-256。SKILL.md、引用资料、脚本、模板和许可证一起检查。不是只看导入后的搜索简介。
2. **拆出可检验声明。** 把“审计数据”“管理文件”“检查安全”等笼统名称拆成具体任务、输入、输出、必要条件、禁止动作和明确排除项。标清哪些是作者写的，哪些是审查员为了测试而操作化的。
3. **做跨文件事实核验。** 例如文档的 CLI 参数在脚本中是否有静态声明，引用文件是否随包提供，总分中的项目是否真被测量。脚本只解析语法树，不导入、不执行。
4. **逐维评价并保留反证。** 每项结论附文件、行号、原文与哈希；冲突或不足进入复核，不能强行补分。引用真实存在，只证明可追溯；仍须检查它是否真正支持结论。
5. **用独立参照验证评价器。** 两位真实评审者盲评，第三位仲裁，比较算法与独立标签，检查引用语义、误报漏报、偏差和覆盖成本。
6. **用产物验证能力与价值。** 固定其他条件，只增加这一份 Skill；以独立验收器测量产物是否合格，比较有/无 Skill 的成功、失败、风险和成本。

大模型在这里可以帮助理解长文和提出候选判断；它不能自封为金标准。当前三个案例由本 Agent 做静态审查，不是假装已经有独立专家结论。

## 3. 怎样规定能力边界

边界不是一个领域标签，也不是一句“擅长数据分析”。一份边界记录至少需要七部分：

| 部分 | 例子：数据审计 Skill 的 CSV 配套模块 |
|---|---|
| 任务 | 读取数据、统计质量问题、输出审计报告 |
| 输入 | 此模块明确读取 CSV；XLSX 支持没有由这段实现建立 |
| 输出与验收 | 行数、缺失、重复、时效等具体结果；不能只交自报总分 |
| 环境 | 所需解释器/依赖、可用内存等；未说明或未测试就保留未知 |
| 权限 | 输入可读且已授权；不擅自修改原始数据 |
| 资源预算 | 时间、内存、规模、调用上限；本案例没有测得可承诺上限 |
| 排除/失败处置 | 文档排除数据库架构、ETL 实现和财务模型验证；不确定的修复先人审 |

这里有三个层次：**声明边界**来自作者材料；**操作化边界**是研究者将其变成测试条件；**经验边界**来自真实执行。前两个可以帮助拒绝明显不适用的请求，但不能冒充第三个。

预检程序已经能输出：匹配文档条件但未执行、前提不满足、前提未知、明确范围外、禁止动作、范围未知。它不会输出“已验证能完成”。输入事实由任务/环境适配器或审查记录提供；当前原型并不验证这些事实的真实性，因此也不是操作系统安全隔离器。

例如，天气数据生命周期 Skill 处理的是文件何时保留、何时释放，不证明天气预测准确。交互视图仍在读取时不能清理；归属不明时应暂停确认；请求清理不能删除共享缓存或用户导出。范围外任务被正确拒绝，是边界遵守，不是天气任务成功。

经验边界最终应写成：“在模型 M、Agent A、环境 E、预算 B、输入范围 X 内，N 个独立任务的成功率及置信区间是多少。”没有测试的大文件、其他模型和其他平台都不能自动包括进来。有限测试不能证明所有未来输入都成功。

## 4. 怎样判断好、坏、未知

材料质量使用八个维度，每维 0–4，有明确档位锚点；材料不可得或无法判断为 unknown，分数为空。完整锚点见 [评分锚点](RUBRIC.md)。

| 维度 | 主要判断依据 |
|---|---|
| 契约一致性 | 声明、步骤、脚本、产出和限制是否相互支持 |
| 完整性 | 必要输入、依赖、资源、流程、异常与输出是否齐备 |
| 静态可操作性 | 命令/接口或决策程序能否具体遵循，而不是靠猜 |
| 验收设计 | 能否借助独立事实发现错误，而不是自称完成 |
| 可维护性 | 版本、依赖、故障诊断、替换与更新是否可追踪 |
| 来源与许可证据 | 固定来源、指纹、组件与许可声明是否可查 |
| 成本意识 | 是否约束时间、算力、存储、重试与费用 |
| 安全边界说明 | 是否明确权限、外部数据、路径与风险处置 |

一般含义：0 是已确认严重缺陷，1 是重大缺口，2 是部分充分，3 是主要要求充分，4 是具体且可交叉核查地充分。每一维的具体含义不同，不能只凭这句通用描述评分。咨询型 Skill 没有脚本不能因此判差，反面教材含“危险”词也不能因此判恶意。

最终结论分开写：材料充分/有缺陷/待核验；任务适用/不适用/未知；实测有效/无明确增益/有害/未测；风险门禁通过/复核/阻断/未知。“好”需要说明对什么用途、在哪些条件下、由什么证据支持。“坏”需要具体缺陷及影响，不能用无标签、名气小或篇幅短来代替。

本轮没有将三个案例硬填成八维数值分，更没有把当前 Agent 的评分冒充独立标签。先锁定尺度，再做独立校准，是避免自说自话的必要步骤。

## 5. 已经做出的三个真实案例

三个案例全部来自可开发的 D1，按解释机制的目的选取，不是随机总体抽样；没有用 D2 案例调方法。原有快照文件包含全库记录，但本轮只把这三个 D1 对象传入资源审查和输出。

### 案例 A：data-quality-auditor

我们读取了 SKILL.md、参考资料、三个 Python 脚本和署名文件。静态交叉核验发现：文档的 DQS 数据质量总分包含唯一性 15% 和时效性 10%，但 `scripts/data_profiler.py:117` 将 uniqueness 固定为 90，`:120` 将 timeliness 固定为 85，邻近注释也注明是 placeholder/default。两项合计 25% 权重，固定贡献 22 分。

这是输入数据的质量总分，不是本研究给 Skill 的评分。它证明该脚本并没有实际测量这两项；如把该总分解释为重复与新鲜度均已验证，会过度解读。它不证明整份 Skill 毫无用处：Agent 仍可能通过其他步骤补测，缺失分析和异常检测也需要分别评价。文档第 47 行还说明脚本分数基于完整性/一致性信号，报告须同时保留这条限定，不能只挑宽泛承诺。

当前结论：具备具体审计流程与脚本；DQS 某些分量不能当作真实测量证据，需复核和补测。不是“已确认安全”“实际任务通过”或“整个 Skill 判坏”。独立验收必须直接检查重复/日期事实，而不是接受它的高分。

### 案例 B：weather-data-lifecycle-management

它明确区分请求工作区、交互会话、共享缓存、用户导出和临时部分文件，说明各自所有者和释放时点，并列出取消/失败处理及检查清单。我们据此做出可运行的边界预检：关闭且归属明确的会话进入“匹配文档条件但未执行”；仍有消费者时前提不满足；归属未知时不能放行为已知；删除共享缓存/用户导出进入禁止动作。

当前结论：材料中的能力边界具体，可转为可检验的生命周期约束。这是正向文档证据；尚不能据此宣布它在 Qt、多进程或实际文件系统中全部正确，也不把它用于预测天气准确性。

### 案例 C：solidity-security

没有只看 42 行的主文档就判它内容不足，而是继续读取约 14 KB 的配套 playbook。它包含安全模式、反例、检查清单和测试示意。跨文件检查发现 playbook 第 499–506 行列出的 8 个本地参考/模板/脚本，均未出现在当前登记包中，包括 `scripts/analyze-contract.sh`。

当前结论：这些引用在当前包中无法兑现；涉及这些资源的使用路径需要补齐或改写。建议性内容仍可阅读，未据此断言所有建议错误。文档中的漏洞代码是教学反例，不据此判恶意；也不能用安全建议代替真实编译、攻击测试或专家审计。

旧规则在这三个案例中都给出 executability=Good、safety=Good；旧总先验重算分别为 0.77、0.69、0.77，存储原值均为空而使用默认先验 0.6。这些数值不是成功概率。新检查增加了明确的实现缺口与适用条件证据，但这三个例子不能估计旧方法总体误判率或证明新方法总体更准。

## 7. 方法可信度高不高，凭什么

**当前判断：证据可追溯与工程约束已经有检查支持；语义评分准确性、能力边界准确性、风险识别率和真实收益尚不能称为高可信。**

| 层次 | 目前证据 | 当前能作的判断 |
|---|---|---|
| 可追溯性 | 版本、指纹、行号、原文；伪造/过期引用负例 | 有可复核机制，限已检查输入 |
| 结论正确性 | 三个本 Agent 静态案例，无独立标签 | 有具体可反驳发现，尚无总体准确率 |
| 评审稳定性 | 没有正式多评审/换位结果 | 未测 |
| 能力与安全效度 | 没有隔离实跑、独立安全金标准 | 未建立 |
| 外部泛化 | 来源集中，正式独立留出尚待修正 | 不支持跨生态普遍结论 |

为什么这个设计有望更可信：它限制结论的证据层级，能追查出处，保留未知，允许反证，要求独立裁决和真实对照。为什么还不能说“已经高可信”：有出处的引用也可能无关，两个评审可能一起错，验收器可能漏需求，样本可能偏，模型和环境还可能变化。必须用后面的验证补齐，而不是用机制名称代替效果。

格式依据来自 [Agent Skills 官方规范](https://agentskills.io/specification)，并不等于效果认证。模型评审的应用与偏差可参见 [G-Eval](https://aclanthology.org/2023.emnlp-main.153/) 和 [Judging the Judges](https://aclanthology.org/2025.ijcnlp-long.18/)；真实价值测量参考 [SkillsBench v4](https://arxiv.org/html/2602.12670v4) 的独立产物验收和有/无 Skill 对照原则。借鉴已发表方法不能继承其准确率，也不构成它们对本项目的背书。

## 8. 对比其他方法，优势怎样证明

| 方法 | 能提供什么 | 主要不足 | 我们应比较什么 |
|---|---|---|---|
| 原有关键词/步骤数启发式 | 便宜、可重复、适合做基线 | 原卡片未覆盖完整实现，词数不等于能力 | 共同维度的人审误差及误放行 |
| 直接让模型打分 | 能理解语义、部署快 | 可能受包装、位置、注入和自评偏好影响 | 同材料同模型同预算的准确度/稳定性 |
| 完整包静态规则 | 路径、接口、依赖等事实可核查 | 覆盖有限，不验证实际任务 | 强规则基线，控制信息增量 |
| 证据约束 + 冲突/未知 + 独立复核 | 可追溯、可升级人审、可定位失配 | 需要成本，仍可能引用无关或共同误判 | 相同覆盖率下误差、风险与总成本 |
| 人类专家审查 | 专业语义和风险判断 | 贵、慢、也可能分歧 | 双盲独立标签、工时和一致性 |
| 真实任务配对试验 | 测实际能力与条件化增益 | 成本高且外推范围有限 | 有/无 Skill 成功差、风险及费用 |

上述是机制差异，不是已经得到的排行榜。尤其是新方法看完整包、旧方法只看卡片时，改善可能来自信息更多，不能全算作算法贡献。要设置同材料的规则与普通模型基线，再逐项移除资源核验、引文、未知、独立复评，测每一部分的实际增量。

“比以前强”的正式证据应是：在来源隔离的测试集、相同材料/预算或清晰披露预算差异的条件下，和独立人审更一致，在覆盖足够正常样本的同时减少错误放行；如果还声称“能挑到更有用的 Skill”，则必须进一步提高独立验收的任务成功率或降低同质量成本。结果无优势也要报告。

## 9. 接下来怎样把第一阶段做完

详细设计见 [方法验证协议](VALIDATION_PROTOCOL.md)。顺序为：

1. 用 D1 训练独立评审，修订并冻结评分锚点、任务契约、偏差测试、主比较和通过规则；当前版本是开发规格，不冒称完成了正式预注册。
2. 补独立来源、语义去重和有效留出材料，完成双人盲评与第三人仲裁；披露仲裁前一致性、未知率和专家覆盖。
3. 在同材料、同模型、同预算下比较原规则、强静态规则、普通模型评审和证据约束方法，报告误差—覆盖—风险—成本。
4. 建立隔离任务环境和由独立人员复核的隐藏验收器，先测正常/边界/错误对照，再做单 Skill 有/无对照执行。当前不在宿主机执行社区脚本。
5. 给每个 Skill 交付有证据的质量画像、声明/操作化/经验边界、失败清单和条件化收益；保留负结果。只有完成这些，才将证据作为固定输入进入第二阶段网络优化。

预算尚未批准的研究批量调用、真实人类标注和隔离执行仍需相应资源；这不妨碍本轮完成免费的机制实现与可审查规格，也不能用本轮工程诊断替代未来实证。

第二阶段将改变“选哪些 Skill、怎样连接和执行”的策略，并与未使用该策略的同一系统比较。它的成功标准是任务成功、边界遵守、安全、成本、延迟与覆盖的联合改善；不是网络节点变多、关系更多或图更好看。本轮没有将网络变化混入第一阶段。
